SHEET 01

先搞懂問題:為什麼「取模雜湊」會出事

要做到水平擴展,必須把請求/資料有效率、平均地分散到多台伺服器上。最直覺的做法是:serverIndex = hash(key) % N(N 是伺服器數量)。這個做法在伺服器數量固定不變時運作良好,但只要 N 一變,就會出大事。

KeyHashhash % 4
(4 台伺服器)		hash % 3
(server 1 離線後)
key0...12
key1...20
key2...00
key3...12
key4...31
key5...00
key6...20
key7...12

紅色標記的欄位代表「伺服器指派結果變了」。書中這個例子只是拔掉 1 台伺服器(server 1 離線,N 從 4 變成 3),結果 8 個 key 裡有 6 個全部要搬家 — 不只是原本存在 server 1 上的 key,而是幾乎所有 key 都被重新分配到不同伺服器,造成一波大規模的快取未命中(cache miss)風暴。

一致性雜湊(Consistent Hashing)就是為了解決這個問題而生的技術。引用 Wikipedia 的定義:當雜湊表重新調整大小時,一致性雜湊平均只需要重新對應 k/n 個 key(k 是 key 的數量,n 是槽位數量),而不是像傳統雜湊表那樣幾乎全部重新對應。

SHEET 04

基本做法的兩個問題,跟虛擬節點解法

問題一:分區大小不平均

伺服器會被加入或移除,環上每台伺服器分到的「分區」(partition,兩台相鄰伺服器之間的雜湊空間)大小很難保持一致。例如伺服器剛好雜湊到彼此很靠近的幾個點,就會有人分區超大、有人分區超小:

之前 — 4 台伺服器,分區大小天差地遠

s0、s1 分到的扇形很小,s2、s3 卻分到一大片 — 誰負擔重、誰負擔輕,完全看運氣。

虛擬節點後 — 每台伺服器變成好幾個小分區

同樣 4 台伺服器,各給 3 個虛擬節點後,分區數變多、每塊也變小變平均,四種顏色的總面積趨於接近。

問題二:key 分佈不均勻

就算伺服器本身分區大小還算正常,實際的 key 也可能剛好大量集中落在某一段範圍裡,導致某台伺服器爆量、其他伺服器閒置:

之前 — 8 個 key 剛好全部擠進同一段

4 台伺服器間距其實很平均,但 8 個 key 全部落在 s1 的範圍內,s0、s2、s3 完全沒有負擔。

虛擬節點後 — 同一批 key 被拆開分散

同樣 8 個 key、同樣的雜湊值,因為環上多了更多虛擬節點可以攔截,被拆分給不同伺服器,不再全部擠向同一台。

解法:虛擬節點(Virtual Nodes) 每台實體伺服器不再只對應環上 1 個點,而是對應多個虛擬節點(例如 s0_0、s0_1、s0_2 都代表伺服器 0)。查找方式不變,一樣是從 key 位置順時針走,找到第一個虛擬節點,再回推它屬於哪台實體伺服器。

每台伺服器的虛擬節點數標準差(相對平均值)
100 個約 10%
200 個約 5%

虛擬節點越多,標準差越小、資料分佈越平均,但也需要更多空間儲存虛擬節點的資訊 — 這是一個可以依系統需求調整的取捨(trade-off)。上面實驗室的滑桿就是在玩這個參數。

SHEET 05 — 課外補充

業界真實案例:一致性雜湊被用在哪裡

書末原文就列出了好幾個真實採用一致性雜湊的系統,這裡挑三個展開說明,點開看細節就好,不看也不影響你理解本章。

案例 01
Akamai CDN:一致性雜湊最早的大型實戰場
對照 SHEET 03．雜湊環怎麼運作
+

背景一致性雜湊這個概念,最早是由 MIT 的 Karger 等人提出的學術成果,而 Akamai(全球最大的 CDN 服務商之一)正是最早把這套理論真正用進大型正式環境的公司之一 — 這也是為什麼書末的真實案例清單裡,Akamai CDN 被特別列出來。

為什麼 CDN 特別需要它CDN 的快取伺服器每天都在增增減減(擴容、汰換機器、機房維護),如果用傳統取模雜湊,每次異動都會讓大量使用者請求被重新導向到不同的快取節點,等於瞬間製造一波大規模快取未命中,原本的效能優勢會被自己的維運動作打掉。一致性雜湊讓機器的增減只影響環上一小段範圍,CDN 才能一邊營運一邊擴充,不會因為換機器而全面影響服務品質。

對理解本章的幫助:一致性雜湊不是教科書裡的理論玩具,它是為了解決「CDN 這種節點數量常態性變動的系統」真實痛點而生的技術。

案例 02
Amazon Dynamo:虛擬節點的經典教科書實作
對照 SHEET 04．虛擬節點
+

背景Amazon 內部的分散式鍵值儲存系統 Dynamo,在其公開論文中把一致性雜湊當作資料分區(partitioning)的核心機制,也是本書第六章要設計的鍵值儲存系統的主要參考對象之一。

虛擬節點解決異質硬體問題Dynamo 論文裡特別提到一個實務考量:不同伺服器的硬體規格不一定相同,有些機器效能好、容量大,有些比較舊、容量小。靠虛擬節點,可以讓效能好的伺服器分配到更多虛擬節點(因此在環上佔比更大、分到更多 key),效能較差的伺服器分配少一點虛擬節點 — 這跟本章單純「讓分佈更平均」的虛擬節點用法相比,是更進一步的應用:虛擬節點數量本身也能拿來當作「這台機器能扛多少」的控制旋鈕。

對理解本章的幫助:虛擬節點不只是用來「補救隨機分佈不均」,還可以反過來當成一個設計參數,刻意讓強者多扛一點、弱者少扛一點。

案例 03
Discord:用類似技巧把 5 百萬人同時在線撐住
對照 SHEET 01．重新雜湊的問題
+

背景聊天軟體 Discord 在公開的工程部落格〈How Discord Scaled Elixir to 5,000,000 Concurrent Users〉中,說明了他們如何把使用者所在的群組(guild)分散到後端一群處理節點上。書末原文也把 Discord 列為一致性雜湊的真實採用案例之一。

為什麼重點是「別讓節點異動影響全局」Discord 的聊天服務要能隨時增減後端處理節點來應付流量變化(跟第一章「無狀態網頁層可以 auto scaling」是同一個精神),如果節點一增減就導致大量群組被重新分配到不同機器,等於每次擴縮容都要付出一次大規模的連線中斷、狀態搬遷代價。用類似一致性雜湊的技巧,讓節點增減只影響一小部分群組,才能讓擴縮容這件事做得又快又不擾民。

對理解本章的幫助:一致性雜湊帶來的「異動範圍可控」,不只是省資料庫查詢成本,對聊天這種需要維持長連線的系統來說,更直接關係到使用者連線會不會被無故中斷。

SHEET 06 — 最終蓋章

本章重點回顧

一致性雜湊也呼應了第一章「分片」小節提過的兩個難題:resharding(重新分片)很痛、名人問題(hotspot key)很麻煩 — 這一章給的就是那兩個問題的具體解法。

  • 伺服器增減時,只需重新分配極少數 key
  • 資料分佈更平均,水平擴展更容易
  • 能緩解「名人問題」(熱點 key 造成單一伺服器過載)
  • 查找邏輯:從 key 位置順時針走到第一台伺服器
  • 基本做法有兩個問題:分區不均、key 分佈不均
  • 虛擬節點是標準解法,節點數越多分佈越平均,但更耗空間
  • 新增/移除伺服器時,只有逆時針方向到下一台伺服器之間的 key 受影響
  • 真實案例:Dynamo、Cassandra、Discord、Akamai CDN、Maglev
