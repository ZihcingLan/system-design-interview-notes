System Design Interview — An Insider's Guide

第三章：系統設計面試框架

A Framework for System Design Interviews — 這不是一場「誰能設計出完美系統」的考試,而是一場模擬「兩個同事一起解決模糊問題」的過程。過程比結果重要。

SHEET 01

面試官到底在看什麼？

沒有人期待你在一小時內設計出一個要幾百幾千位工程師才能蓋出來的真實系統。面試考的是「解決模糊問題的過程」,不是最終設計本身。

  • 協作能力：能不能把面試官當隊友一起討論,而不是自己悶頭solo。
  • 抗壓表現：面對開放式、沒有標準答案的問題,是否還能有條理地往前推進。
  • 化解模糊的能力：問題一開始通常又大又模糊,怎麼把它拆解、聚焦。
  • 提問能力：很多面試官特別看重「你會不會問對問題」這件事本身。

面試官在找的紅旗警訊：

  • 過度工程(Over-engineering)：工程師的職業病 — 沉迷於設計上的「純粹」,卻忽略了真實世界的取捨(trade-off);許多公司都為這種不自覺的過度設計付出高昂代價。
  • 思維狹隘、固執己見：聽不進去回饋、只想照自己原本的想法走到底。

    SHEET 03

    該做／不該做

    書末給的整理,幾乎每一條都跟「溝通」有關,而不是技術本身。

    DO'S

    • 永遠先問澄清問題,不要假設你的假設是對的
    • 先搞懂問題的需求範圍
    • 沒有唯一正確答案 — 新創公司跟千萬用戶的成熟公司,合理設計完全不同
    • 讓面試官知道你在想什麼,持續溝通
    • 盡量提出多種可能的做法
    • 跟面試官對藍圖達成共識後,再逐一深入細節,先做最關鍵的元件
    • 把想法丟出來跟面試官討論,把她當隊友
    • 永不放棄

    DON'TS

    • 不要對常見面試題目毫無準備
    • 不要還沒釐清需求跟假設就急著跳進解法
    • 不要一開始就在單一元件上鑽牛角尖,要先給高層設計再往下挖
    • 卡住的時候不要不敢開口要提示
    • 不要悶頭思考不說話,要溝通
    • 提出設計不代表面試結束 — 面試官說結束才算結束,要主動、常態性地要回饋

    案例 01
    NASA 火星氣候探測者號:一個沒問清楚的單位換算
    對照 SHEET 02．Step 1 理解問題
    +

    真實事件1999 年,NASA 的火星氣候探測者號(Mars Climate Orbiter)在準備進入火星軌道時解體損毀,整個任務耗資約 3.27 億美元。事後調查發現,問題出在其中一個地面軟體團隊用「英制單位(磅力·秒)」計算推力數據,但探測器的導航系統預期收到的是「公制單位(牛頓·秒)」— 雙方都沒有明確核對過這個假設。

    跟本章的關聯這正是書裡「Jimmy 的故事」想提醒的反面教材:太快跳進解法、不先把假設攤開來核對,問題會被隱藏到最後一刻才爆炸。系統設計面試裡,「你的使用者是幾百萬人還是幾千人」「這個 ID 是 64 位元還是 128 位元」這種問題如果沒問清楚,做出來的設計方向可能整個是錯的 — 差別只是面試的代價是分數,真實世界的代價可能是幾億美金。

    對理解本章的幫助:寫下假設、標清楚單位,不是形式主義,是實際會讓系統失敗或成功的關鍵動作。

    案例 02
    《人月神話》的「第二系統效應」
    對照 SHEET 01．過度工程紅旗
    +

    經典理論軟體工程師 Fred Brooks 在經典著作《The Mythical Man-Month(人月神話)》中提出「第二系統效應(Second-System Effect)」:工程師做完一個簡單、克制、成功的第一個系統後,做「第二個系統」時往往會忍不住把所有想加的花俏功能、想耍的技巧全部塞進去,結果做出一個過度複雜、臃腫、難以維護的系統。

    跟本章的關聯這就是書裡說的「過度工程是工程師的職業病」的經典理論根源 — 面試官很敏感地在抓這個訊號:你是不是為了展示自己會很多技術,硬把消息佇列、多資料中心、分片全部塞進一個原本用不到這麼複雜架構的設計裡?好的系統設計是「剛好夠用」,不是「用上所有你會的招式」。

    對理解本章的幫助:面試時可以自問一句「這個元件是題目真的需要,還是我只是想展示我會?」— 這正是面試官想看到你有沒有的判斷力。

    案例 03
    Google 的結構化面試:為什麼「過程」比「答案」更容易評分
    對照 SHEET 01．面試官在看什麼
    +

    真實做法Google 前人資長 Laszlo Bock 在《Work Rules!》書中提到,Google 長期採用「結構化面試(structured interview)」— 面試官依照固定的評估準則(rubric)給訊號,再交由獨立的「招募委員會(Hiring Committee)」根據多位面試官的書面回饋,而不是單一面試官的主觀好惡,共同決定是否錄取。

    跟本章的關聯這也解釋了為什麼系統設計面試官會反覆說「沒有標準答案,重點是過程」— 因為結構化面試的評分本來就不是看「你設計出的架構圖跟正解一模一樣嗎」,而是看你有沒有展現出可以被具體記錄下來的訊號:有沒有問對問題、有沒有考慮 trade-off、遇到回饋會不會調整。這些「訊號」才是委員會真正拿去比較不同候選人的依據。

    對理解本章的幫助:與其想著「怎麼答出正解」,不如想著「我要怎麼讓面試官事後寫報告時,有具體的例子可以引用來證明我的能力」。

    SHEET 05 — 最終蓋章

    本章重點回顧

    系統設計面試考的是解決模糊問題的過程,不是設計出完美系統。

    • 先問清楚,不要急著給答案
    • 先出高層設計,取得面試官認同再深入
    • 用概略估算驗證你的藍圖撐不撐得住
    • 時間管理:理解→設計→深挖→收尾
    • 主動指出自己設計的瓶頸與可改進處
    • 全程跟面試官保持溝通,把她當隊友
