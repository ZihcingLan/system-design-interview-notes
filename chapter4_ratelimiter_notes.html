SHEET 01

為什麼需要限流器？放在哪裡？

限流器(Rate Limiter)限制一段時間內允許送出的請求數量,超過門檻的請求全部擋掉。例如:同一 IP 一天最多開 10 個帳號;同一裝置一週最多領 5 次獎勵。

三個好處：

  • 防止資源耗盡 / DoS 攻擊：大公司的 API 幾乎都有限流,例如 Twitter 限制每 3 小時最多 300 則推文,Google Docs API 預設每位使用者每 60 秒最多 300 次讀取請求。
  • 降低成本：擋掉多餘請求代表少用一點伺服器資源;如果你的系統要付費呼叫第三方 API(查信用、扣款、調病歷),限流是控制成本的關鍵。
  • 避免伺服器過載：擋掉機器人或異常行為造成的過量請求,減輕伺服器負擔。

客戶端請求很容易被偽造,不是可靠的執行點。伺服器端限流讓你完全掌控演算法,但如果已經在用 API Gateway(統一做認證、SSL、IP 白名單等),把限流也放進去通常更省事;要不要自己蓋一套,取決於你的技術棧和工程資源。

SHEET 04

高層架構與分散式環境的兩個難題

基本架構：用記憶體快取(不用資料庫,磁碟太慢)存計數器,Redis 是常見選擇,搭配兩個指令:INCR(計數器 +1)跟 EXPIRE(設定逾時,時間到自動清除計數器)。中介層先向 Redis 查計數器,沒超標才放行到 API 伺服器,同時把計數器 +1 寫回去。

難題一:競態條件 Race Condition

高併發下,兩個請求同時讀到計數器是 3,各自 +1 後都寫回 4 — 正確答案應該是 5。常見解法是用 Lua Script 或 Redis 的 Sorted Set 資料結構把「讀取+判斷+寫入」變成一個原子操作,避免用鎖(鎖會拖慢系統)。

難題二:多台限流伺服器的同步

Web 層是無狀態的,同一個客戶端的請求可能被導到不同台限流伺服器,若各自維護計數器就會各算各的。用「黏性連線」硬綁客戶端到同一台不夠靈活也不好擴展;更好的做法是全部限流伺服器共用同一個集中式資料存放區(如 Redis)。

效能優化：跨區使用者延遲高,建議像 Cloudflare 那樣在全球佈署多個邊緣節點(截至書中寫作時 Cloudflare 有 194 個),就近處理限流判斷;多節點間的資料同步則採用最終一致性模型換取效能。

SHEET 05

限流規則、回應碼與標頭

規則怎麼定義：Lyft 開源了他們的限流元件,規則寫成設定檔存在磁碟上,例如「行銷訊息類別,每天最多 5 則」或「登入類別,每分鐘最多 5 次」,由背景程式定期把規則從磁碟載入快取。

被擋下來會怎樣：回傳 HTTP 429 Too Many Requests。依情境不同,有時會把被擋的請求放進佇列稍後處理(例如系統過載時暫緩訂單,而不是直接丟棄)。

客戶端怎麼知道自己被限流：靠回應標頭:

標頭意思
X-Ratelimit-Remaining這個窗口內還剩幾次可用
X-Ratelimit-Limit這個窗口總共允許幾次
X-Ratelimit-Retry-After要等幾秒才能再送請求

業界真實案例：這些演算法怎麼被真的用

案例 01
Stripe 公開部落格:如何在多台機器間跑同一個權杖桶
對照 SHEET 02．權杖桶模擬器
+

真實做法付款平台 Stripe 在自家工程部落格公開過他們限流器的設計思路:因為 API 請求會分散打到很多台伺服器,如果每台伺服器各自維護一個獨立的權杖桶,同一個客戶的真實請求量就會被低估(每台桶都以為自己是唯一的桶)。Stripe 因此把權杖桶的狀態集中放進共用的記憶體儲存,讓所有伺服器看到的是同一個桶子。

對理解本章的幫助:這正好呼應本章「分散式環境的同步難題」— 光懂演算法本身不夠,權杖桶、固定窗口這些邏輯一旦要跨多台伺服器運作,「狀態放在哪裡」才是真正的工程難題。

案例 02
Cloudflare:4 億次請求裡,滑動窗口計數器的誤差只有 0.003%
對照 SHEET 03．演算法總表
+

真實數字Cloudflare 在自家工程部落格公開過一次實驗:他們用滑動窗口計數器演算法(假設請求在窗口內平均分佈的近似演算法)處理了約 4 億筆請求,結果只有 0.003% 的請求被錯誤地放行或錯誤地擋下。

為什麼重要滑動窗口計數器理論上是「近似值」,不像滑動窗口日誌那樣 100% 精準。但 Cloudflare 的真實數據證明,在他們的真實流量規模下,這個近似的誤差小到可以忽略 — 换来的是省下大量記憶體與運算成本,是一個「用可接受的精準度換取效能」的典型工程取捨案例。

對理解本章的幫助:面試被問「這個演算法只是近似值,能接受嗎?」時,Cloudflare 這組真實數字是很有說服力的參考點。

案例 03
Shopify 為什麼選漏桶,而不是允許爆發的權杖桶
對照 SHEET 03．演算法總表
+

真實做法電商平台 Shopify 的 REST Admin API 採用漏桶演算法做限流,官方文件公開說明了具體的桶子容量與固定流出速率。

為什麼是漏桶,不是權杖桶權杖桶允許「短暫爆發」— 只要桶子裡還有累積的權杖,瞬間衝一波請求也能全部通過。但電商後台系統(例如商品同步、訂單處理)通常更在意「下游處理速度穩不穩定」,不希望瞬間湧入一大波請求打爆後端資料庫。漏桶用固定輸出速率處理請求,不管前面湧入多猛,後面吐出去的速度永遠是穩定的 — 這正好符合電商場景「寧可穩定、不要爆發」的需求。

對理解本章的幫助:選演算法不是背答案,是看場景 — 社群平台按讚可以允許爆發用權杖桶,電商後台寫入資料庫可能更適合漏桶的穩定輸出。

SHEET 07 — 最終蓋章

本章重點回顧

額外可以聊的延伸話題:硬性限流(超過門檻絕對擋下) vs 軟性限流(允許短暫超過門檻);限流也可以做在網路層(IP,Layer 3)而不只是應用層(HTTP,Layer 7);客戶端最佳實務是善用快取、瞭解限制、加上重試的退避時間。

  • 限流器放中介層 / API Gateway 最實務
  • 權杖桶允許爆發,漏桶輸出速率穩定
  • 固定窗口簡單但有邊界突發問題
  • 滑動窗口日誌精準但耗記憶體
  • 滑動窗口計數器是精準度與效能的折衷
  • 計數器放 Redis,善用 INCR / EXPIRE
  • 用 Lua Script 或 Sorted Set 解決競態條件
  • 多台限流伺服器要共用集中式資料存放區
